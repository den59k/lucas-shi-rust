# 8-bit versus f32 pipeline

Host measurements on 2026-10-17, Apple M2 (8 cores), with moderate background
load (load average 3-5). Native target `aarch64-apple-darwin`; WASM target
`wasm32-wasip1` with the repository's `simd128` configuration, run by Node
v22.22.2 / WASI preview1 on the same host. Stable Rust 1.99.0 (`b940084d7`,
LLVM 23.1.1), release profile (opt-level 3, LTO, one codegen unit),
Criterion 0.8.2. Source: `9a4cca8` (`float-features`) plus
[`benches/float.rs`](../float.rs). These numbers describe this host, not a
deployment device or a browser.

## Method

`cargo bench --bench float` times each stage with a warmed context of each
pipeline (`DetectorContext` / `TrackerContext` against `FloatDetectorContext` /
`FloatTrackerContext`), so no allocation is timed. Image generation happens
before timing. Each case uses 30 samples, 0.7 s warm-up and 2 s measurement.
The tables give the Criterion mean of two complete rounds (round 1 / round 2)
and the f32 / 8-bit ratio of each round. Native and WASI runs did not overlap.

Inputs:

- `example_720x405` (bundled frame) and `texture_640x480` (seeded smoothed
  texture) give both pipelines the same pixel values: the f32 frame holds the
  8-bit values. Detection returns identical corners (60 and 2727) and tracking
  identical statuses, so the ratio is the cost of the f32 implementation.
- `thermal_640x480` is the deployment comparison: a synthetic frame in °C (22-26
  °C background gradient, warm bodies up to 36 °C, structure of a few tenths of
  a kelvin, 40 mK noise). The 8-bit pipeline maps it to grey levels with a fixed
  20-220 °C range (0.78 K per level, `convert`); the f32 pipeline validates it
  as a `FloatImageView` (`validate`). These workloads differ, see below.

Stages: `detect_plain` (quality 0.05, spacing 8 px), `detect_grid_top_up` (6x4
grid, 5 per cell, 24 existing points), `prepare` (both pyramids), `track` and
`track_fb` (forward-backward check), and `frame_step`: convert or validate the
new frame, build both pyramids, `track_fb`, and top up the grid around the
surviving points. Tracking configurations: `pipeline` = 3 levels, 15 px window,
15 iterations, 60 points (the configuration of the current ircam pipeline);
`dense` = 4 levels, 21 px window, 30 iterations, 300 points. The frame pairs move
by (3, 2) px. The f32 eigenvalue threshold equals the 8-bit default on 8-bit
values and its scaled equivalent in (°C / px)^2 on the thermal pair.

## Workloads

Counts printed outside timing, identical on native and WASI:

| Input | Detected (plain) 8-bit / f32 | Tracked with FB check, mean error vs. true motion |
|---|---|---|
| example_720x405 | 60 / 60 | – |
| texture_640x480 | 2727 / 2727 | pipeline 60 / 60, dense 300 / 300, both 0.001 px |
| thermal_640x480 | 1343 / 2785 | pipeline 8-bit 39 at 0.68 px, f32 24 at 0.17 px; dense 8-bit 234 at 0.53 px, f32 211 at 0.12 px |

On the thermal frame, quantization to 0.78 K per grey level zeroes the scores of
most weak structure, so the 8-bit detector sorts and spaces fewer candidates.
Its tracker follows the quantization contours: more points pass the
forward-backward check, but with four to five times the position error. The
f32 tracker rejects windows dominated by sensor noise. The thermal detection and
frame-step ratios therefore include a larger f32 workload; with an absolute
threshold above the noise floor, the f32 detector would sort fewer candidates.

## Findings

- **Same data, whole frame step:** f32 costs 1.09-1.10x natively and 1.10-1.15x
  under WASI.
- **Detection** costs 1.08-1.25x natively and 1.18-1.55x under WASI on the same
  data. The per-pixel stages carry the overhead (f32 gradients at half the i16
  lane count, f64 tensor sums); it shows most on the example frame, which has
  few candidates. Sorting and spacing are shared code and cost the same.
- **Tracking is faster in f32:** 0.77-1.01x of the 8-bit time on the same data,
  0.58-0.89x on the thermal pair. The 8-bit kernel converts every u8 sample and
  i16 gradient to f32 for interpolation; the f32 kernel loads them directly.
- **Pyramids** cost 3.2-3.9x, from 0.022 to about 0.08 ms per frame pair: four
  times the bytes, at memory speed.
- **Input preparation:** validating an f32 frame takes 0.02-0.03 ms. The fixed
  8-bit mapping takes 0.06 ms natively but 0.9 ms under WASI, where `f32::round`
  is a library call instead of an instruction.
- **Thermal frame step:** 1.60x natively, 1.23x under WASI, including the larger
  f32 detection workload and the WASI conversion cost of the 8-bit pipeline.

## 8-bit pipeline check

The 8-bit tensor pass, planes and Lucas-Kanade kernel became generic in the same
change. `features` (plain, grid top-up) and `tracking` (`after/*`) were run
against the pull request state `1330056`, alternating per input in two rounds.
Detection changed by -3.4 to +1.5% in all cases except one case per round with
a wide interval (+22% [+1, +62] and +12% [+2, +27]) that the other round did not
reproduce. Tracking was 11-18% faster in every case in both rounds. Outputs are
bit-identical according to the regression fixtures.
