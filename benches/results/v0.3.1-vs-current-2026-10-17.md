# 0.3.1 versus the current revision

Host measurements on 2026-10-17, Apple M2 (8 cores), with moderate background
load (load average 3-6). Native target `aarch64-apple-darwin`; WASM target
`wasm32-wasip1` with `simd128`, run by Node v22.22.2 / WASI preview1 on the same
host. Stable Rust 1.99.0 (`b940084d7`), release profile (opt-level 3, LTO, one
codegen unit), Criterion 0.8.2 on both sides. These numbers describe this host,
not a deployment device or a browser.

Revisions:

- **0.3.1**: the published `optical-flow-lk` 0.3.1 crate. Its `src/` is
  identical to `f34658f`, which was built here (the manifest there still says
  0.3.0).
- **current**: `1dcca4a` (`float-features`), the 8-bit API and the f32 pipeline,
  measured as `3766415` before a rebase onto 0.4.1 that left the sources
  unchanged.

## Method

One harness source, stored as
[`v0.3.1-vs-current-2026-10-17.rs`](v0.3.1-vs-current-2026-10-17.rs) (not built
by Cargo here), was compiled into two benchmark crates: one against the `f34658f`
source tree, using only the 8-bit API both revisions share, and one against this
repository with the harness feature `current`, which adds the contexts and the
f32 pipeline. Both crates use the same lockfile apart from their own package
versions, separate target directories and the same profile. Benchmark IDs carry
the revision, so the two binaries never share a Criterion baseline.

Each case uses 30 samples, 0.5 s warm-up and 1.5 s measurement. Two complete
rounds were run: round 1 ran 0.3.1 and then current, round 2 in the opposite
order, each native and then WASI. No runs overlapped. The tables give the mean
of the two rounds' Criterion means and the speedup over 0.3.1 (0.3.1 time
divided by current time). Per-round means and confidence intervals are in
[`v0.3.1-vs-current-2026-10-17.json`](v0.3.1-vs-current-2026-10-17.json).

Inputs and stages match [`benches/features.rs`](../features.rs) and
[`benches/float.rs`](../float.rs): the bundled 720x405 frame, smoothed textures
at 320x240 and 640x480, a low-contrast texture, a flat image, and the synthetic
thermal frame in °C. The 8-bit pipelines receive the thermal frame mapped with a
fixed 20-220 °C range; the f32 pipeline receives the temperatures. Detection uses
quality 0.05 and 8 px spacing; grid top-up uses a 6x4 grid with 5 points per
cell and 24 existing points. Tracking uses `pipeline` (3 levels, 15 px window,
15 iterations, 60 points) and `dense` (4 levels, 21 px window, 30 iterations, 300
points) on frame pairs moved by (3, 2) px.

Variants of the current revision:

- `u8 free fn`: `good_features_to_track(_grid)`, allocating per call like 0.3.1.
- `u8 context`: a warmed `DetectorContext`.
- `f32 fresh`: a new `FloatDetectorContext` per call, so it allocates like the
  free functions.
- `f32 context`: a warmed `FloatDetectorContext`.

Tracking always uses a warmed `TrackerContext` or `FloatTrackerContext`. The
frame step converts (8-bit, thermal only) or validates (f32) the new frame,
builds both pyramids, runs `track_fb` and tops up the grid around the surviving
points. For 0.3.1 and `u8 free fn`, the top-up is the allocating free function.

0.3.1 returns corners that the corrected detector does not (see the 0.4.0 and
0.4.1 fixes in the [changelog](../../CHANGELOG.md)): 5520 points on both the
flat and the thermal frame, and 867 instead of 60 on the example frame. Its
detection time there includes more sorting and spacing. On the two smooth textures, where 0.3.1
returns fewer corners than the current detector (556 and 2209 against 678 and
2727), f32 plain detection is 2.9-3.1x faster natively and 1.9-2.0x under WASI.

## Findings

- **Whole frame step:** f32 is 3.3-3.6x faster than 0.3.1 natively and 2.9-3.1x
  under WASI, although it computes with f32 gradients and f64 window sums. The
  current 8-bit pipeline is 3.9-5.3x and 3.4-3.9x faster.
- **Detection:** with a warmed context, f32 is 2.9-8.0x faster natively and
  1.9-5.6x under WASI in plain detection, and 3.3-7.3x and 2.2-5.3x in grid
  top-up. A fresh context per call costs at most 5% more than a warmed one.
- **Tracking:** f32 is 3.7-4.0x faster natively and 5.5-6.1x under WASI in the
  `pipeline` configuration, and 8.4-9.8x and 10.2-11.0x in `dense`. Part of
  this comes from the convergence criterion rather than kernel efficiency: 0.3.1
  stops a level once both update components are below 0.001 px; the current
  tracker uses `CONVERGENCE_EPSILON` (0.01 px) and stops on oscillation, so it
  runs fewer iterations, most visibly with the 30-iteration `dense` limit.
- **Pyramids are the only slower stage:** the 8-bit pyramids cost the same as in
  0.3.1 (0.02 ms); the f32 pyramids take 0.08 ms, four times the bytes. The
  difference of 0.06 ms per frame pair is about 2% of the f32 frame step.
